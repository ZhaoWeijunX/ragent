# 测试、api-test 与证据规则

> 最后核验：2026-08-26。目标是让“通过”具有可复现含义。

## 验证顺序

1. 静态引用搜索与 `git diff --check` 证明路径/格式。
2. 受影响模块编译证明类型与映射生成。
3. 目标单元/组件测试证明局部规则。
4. `api-test/scenarios` 证明真实接口、数据库和回调链。
5. 必要时做隔离环境端到端观察。

每项只能证明自己的范围。Maven 因依赖下载或预存测试编译错误失败，不能说目标代码已通过；YAML 存在但未运行，只能列为验证入口。

## 场景设计

业务主链至少包含正常、校验失败、重复请求、旧状态、回调成功/失败/重复、配置缺失和权限/租户隔离。异步文件链还要触发 Job 或直接调用受控测试入口并检查最终状态、历史和后继任务。

## 证据记录

记录命令、时间、checkout、profile/环境、测试数据标识、退出码、关键断言和未覆盖范围；敏感值脱敏。模拟数据要明确标注，不能与生产观察混写。

## 当前资产边界

BL Desk 有较完整 `../api-test/scenarios/bill-desk`；Booking/Release 等主链覆盖并不稳定。具体场景以当前相邻仓库检索为准。来源：POM/Surefire 配置、src/test、api-test README/场景、AGENTS 验证边界。面试追问：测试金字塔如何覆盖异步最终一致性与第三方契约。

## 项目级测试切片

规则策略优先做无外部依赖的参数化单测，例如针对 Bill/VGM/Manifest 的 carrier/channel、processType、Bean Validation group 和跨字段规则；Processor 测试再验证 TEMP 与正式提交分支、配置解析和 DTO 转换；Handler/Receipt 测试使用已有记录覆盖旧状态条件、重复回执和后继任务；Controller/api-test 最后证明协议、数据权限和真实持久化组合。

对于 MapStruct/Mongo round-trip 字段，测试必须同时验证 API DTO → 领域对象 → Mongo Document 和反向读取，避免“能接收但详情丢字段”。对于 MyBatis-Plus 更新，清空错误信息应断言空串/null 的真实写入行为。对于文件流程，断言 schedule job 类型、文件记录和主状态，而不只断言方法返回 true。

## 异步断言策略

不要用固定长睡眠替代条件等待。以业务 id 轮询明确终态，设置合理超时，并在超时时输出任务、当前态和最后错误。重复/乱序用例应显式发送相同 taskNo 或旧回执，断言状态未回退、历史没有不合理重复。外部 client 使用 mock 时保留 HTTP status、body 和业务 code 三层合同。

## 失败结果怎样报告

把“目标断言失败”“测试源码编译失败”“依赖解析失败”“环境连接失败”分开。只有第一类直接反证目标行为；其余只说明验证未完成。报告应给第一条相关错误、受影响模块和下一种可用验证，而不是截取 Maven 最后一个 `BUILD FAILURE`。
